# План интеграции с реальным гражданским оборудованием

Первая версия работает только с симулятором. Реальное управление полётом, автономная навигация
и передача команд полёта **не реализованы** и рассматриваются как отдельный этап с
самостоятельной проверкой безопасности и соответствия законодательству.

## Что уже готово

* Интерфейс адаптера `DroneAdapter` (`drone-agent/fpv_agent/adapters/base.py`): подключение,
  телеметрия, самодиагностика, видеосегменты, события оборудования. Методов управления нет;
  возможность `flight_control` объявлена как `False` (проверяется тестом).
* Бизнес-логика не зависит от модели дрона: сервер работает только с контуром `/drone-link/v1`
  (телеметрия, события, видео, справочная информация о задании).
* Поле `drones.adapter_kind` (`simulator`, `vendor_sdk`, `mavlink_readonly`) для учёта типа интеграции.

## Этап A. Интеграция в режиме «только чтение»

Цель — реальная телеметрия, диагностика и видео без передачи команд.

1. Выбор оборудования из реестра разрешённых гражданских БВС; документированный SDK производителя
   или стандартный протокол (например, MAVLink) в режиме приёма сообщений.
2. Адаптер `vendor_sdk` / `mavlink_readonly`, реализующий `DroneAdapter`; на уровне транспорта
   исходящие сообщения управления блокируются (фильтр по типам сообщений, юнит-тесты).
3. Видео: сегментация потока камеры в MPEG-TS на наземной станции; подпись сегментов ключом
   устройства (защита от подмены на канале) — расширение контура `/drone-link`.
4. Достоверность позиции: учёт `gnss_fix`, отбраковка выбросов; на карте — только достоверные данные.
5. Испытания на стенде (HIL), затем на полигоне с наблюдателем.

## Этап B. Предпосылки для любых команд (решение принимается отдельно)

До рассмотрения передачи команд должны быть выполнены и задокументированы:

* правовая база: регистрация БВС, допуск пилотов, разрешения на использование воздушного
  пространства, требования авиационных властей, страхование;
* требования производителя к интеграции и сертификации;
* учёт ограничений воздушного пространства (официальные источники зон, а не тестовый список);
* механизмы безопасного прекращения операции на борту (возврат, посадка) независимо от связи с сервером;
* отдельный защищённый контур управления: аутентификация оператора и устройства, подтверждение
  состояния системы, двойной контроль критических команд, журналирование, независимая оценка безопасности;
* анализ опасностей (например, по методологии SORA) и модель угроз контура управления.

Платформа доставки остаётся системой учёта, координации и контроля; включение функций управления
в её API без выполнения перечисленного не допускается.
